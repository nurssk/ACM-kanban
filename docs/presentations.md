# Презентации ACM @ NU — описание реализации для разработчиков

Дата: 1 октября 2026.

Документ объясняет, что реализовано во фронтенде, как связаны модули и куда подключать сервер. Это описание текущего кода, а не пользовательская инструкция и не обещание готового backend.

## 1. Что сделано

Реализован встроенный редактор презентаций для встреч клуба. Он использует один ACM-шаблон и три типа слайдов: заголовок, информация и живые задачи одного проекта.

Keystatic не используется. Вместо внешней CMS сделан собственный структурированный редактор: пользователь меняет поля слайда, а приложение формирует его внешний вид. Презентация хранится как объект с массивом слайдов, не как HTML-страница, MDX-программа или файл PowerPoint.

Готовы:

- Библиотека презентаций: список, поиск, создание, открытие, дублирование, архивирование и восстановление.
- Редактор: порядок слайдов, добавление, дублирование, удаление, смена типа, свойства и заметки докладчика.
- Единый рендерер для предпросмотра и режима показа.
- Создание и редактирование общих задач непосредственно из слайда, включая режим показа.
- Удаление задачи с подтверждением и восстановление через «Удалённые» выбранного проекта; данные и комментарии не уничтожаются.
- Автосохранение презентаций, обнаружение конфликтов версий, локальные черновики и JSON-экспорт.
- Общий слой данных с локальным репозиторием и подготовленным HTTP-адаптером.
- Контракт для будущего Cloudflare backend и reference SQL-схема D1.

В проекте React 18, Vite 5, JavaScript/JSX, обычный CSS и Phosphor Icons. Отдельной библиотеки презентаций, Redux, React Router или полноценного Markdown-парсера нет.

## 2. Главный принцип: презентация не хранит копии задач

Презентации и задачи — разные сущности. Слайд задач сохраняет проект и фильтры, затем выбирает подходящие задачи из общего `snapshot.issues`.

```text
workspace snapshot
├── projects
├── issues ─────────────────────────── общий источник задач
│   ├── доска проекта
│   ├── личный список
│   └── слайды типа tickets
└── presentations
    └── slides[]
        └── tickets: projectId + statuses + assigneeId
```

Следствия, которые важно сохранять при доработках:

- Один слайд `tickets` связан ровно с одним проектом.
- Одна презентация может содержать несколько проектов на разных слайдах.
- Изменение задачи из презентации меняет ту же запись, что используется на доске.
- Удаление слайда, дублирование или архивирование презентации не удаляет и не копирует задачи.
- Живой слайд показывает текущее состояние, не исторический отчёт на дату создания презентации.
- Telegram-бот должен работать с общими задачами через сервер, а не читать содержимое слайдов.

## 4. Модель презентации и слайда

Workspace имеет `schemaVersion: 2`. В нём презентации лежат в `presentations[]`, задачи — отдельно в `issues[]`.

Презентация содержит `id`, `workspaceId`, `title`, `owner`, `templateId`, `version`, временные метки, поля автора, `archivedAt` и массив `slides`. Сейчас разрешён только `templateId: "acm-standard-v1"`.

Пример структуры одного слайда задач:

```json
{
  "id": "slide-opaque-id",
  "kind": "tickets",
  "title": "Задачи сайта клуба",
  "body": "",
  "notes": "Обсудить блокеры перед следующей встречей",
  "projectId": "club-site",
  "statuses": ["planned", "progress", "review"],
  "assigneeId": null
}
```

`id` — непрозрачная стабильная строка. `makeSlide()` генерирует UUID; стартовые слайды новой презентации получают ID из ID презентации и суффикса. Нельзя писать логику, предполагающую UUID-формат всех старых и новых ID.

| kind | Содержимое | Поведение |
| --- | --- | --- |
| `title` | `title`, `body` как подзаголовок, `notes` | Крупный титульный слайд |
| `text` | `title`, `body` с ограниченным Markdown, `notes` | Информационный слайд |
| `tickets` | `title`, `projectId`, `statuses`, `assigneeId`, `notes` | Живая выборка общих задач; `body` не рендерится |

У слайда нет собственной версии или поля позиции: порядок определяется массивом `slides`, а версия относится ко всей презентации. Legacy-поле `presentation.projectId` может остаться после миграции, но источник задач определяется именно `slide.projectId`.

Ограничения модели: 1–100 слайдов, уникальные ID внутри презентации, заголовок до 300 символов, body и notes до 20 000. Для `tickets` обязателен непустой projectId и хотя бы один допустимый статус. `assigneeId: null` означает всех участников, а не только задачи без исполнителя.

## 5. Библиотека и создание

`PresentationLibrary` фильтрует активные/архивные записи по `archivedAt`, ищет по названию и сортирует по `updatedAt` от новых к старым. В карточке показываются количество слайдов и число уникальных проектов в слайдах задач.

`Workspace.createPresentation()` создаёт титульный и информационный слайды; если выбран проект, добавляет третий слайд `tickets`. Если проектов нет, презентация может начаться с двух текстовых слайдов.

Дублирование создаёт новый ID презентации и новые ID её слайдов, сохраняя projectId/фильтры. Архивирование — soft archive через команду; восстановление снимает `archivedAt`.

Название презентации и заголовок титульного слайда после создания редактируются независимо: переименование деки не переименовывает слайд автоматически.

## 6. Редактор и сохранение

`PresentationEditor` получает подтверждённую `presentation` через props и держит отдельный редактируемый `deck`. Основные состояния:

- `baseVersion` — версия, на основе которой началось редактирование.
- `dirty` — есть несохранённые изменения структуры/текста.
- `saveState` — состояние сохранения.
- `selectedId` — выбранный слайд.
- `presenting` — открыт ли показ; `showNotes` — открыты ли заметки.

Изменение поля обновляет `deck`, помечает его dirty и записывает черновик. Автосохранение запускается через 700 мс после изменения, если нет текущей записи, конфликта или ошибки. Кнопка «Сохранить» выполняет тот же путь явно.

```text
Изменение поля
  → PresentationEditor.update / changeSlide
  → onSave({ title, slides }, baseVersion)
  → Workspace.savePresentation
  → data.execute("presentation.update", id, fields, expectedVersion)
  → repository.execute(command)
  → подтверждённый snapshot
  → новая presentation.version, очистка dirty/черновика
```

`data.execute()` возвращает snapshot либо `null` при ошибке; ошибка доступна в состоянии хука. `Workspace.savePresentation()` преобразует успешный результат в объект презентации. Метод `editorRef.save()` возвращает признак успешного сохранения, чтобы навигация могла остаться в редакторе при ошибке.

«Показать», возврат к библиотеке и навигация через обработчик `navigate()` сначала пытаются сохранить изменения. При закрытии/перезагрузке страницы с dirty-данными регистрируется `beforeunload`-предупреждение.

Если dirty-презентация получает другую `version`, редактор не перезаписывает её молча. Доступны скачивание черновика и загрузка актуальной записи. Автоматического слияния полей или посимвольного совместного редактирования нет. Если подтверждённые title/slides совпали с черновиком, редактор может признать его сохранённым, в том числе после повторной отправки.

## 7. Создание и редактирование задач из слайда

В `SlideCanvas` нет отдельного task store и прямых запросов к API. Он получает `issues` и callbacks от `Workspace`.

Создание: `onCreateTask(status, project.id)` → `TaskModal` → `issue.create` → общий snapshot. В форме, открытой из редактора презентации, project selector заблокирован; `Workspace.addIssue()` дополнительно подставляет зафиксированный projectId. Это защита UX, не замена серверной проверке прав.

Начальный статус — planned, если он включён в слайде; иначе первый выбранный статус. Начальный исполнитель — текущий участник. Фильтр слайда по исполнителю не назначает новую задачу автоматически: её нужно назначить этому человеку, иначе она не попадёт в выборку.

Редактирование: клик по карточке → общая `IssueSheet` → `issue.update` с версией задачи. Комментарий отправляется отдельно через `issue.comment` и также увеличивает версию задачи. Дедлайн задаётся календарным input и хранится как `YYYY-MM-DD|null`.

После успешной команды доска и слайд получают одну обновлённую запись. Если изменённый статус/исполнитель не проходит фильтр, карточка исчезает со слайда, но задача остаётся в проекте. Версия самой презентации при этом не меняется.

У задачи `id` — технический ключ для связей/бота, а `identifier` — читаемый номер, например WEB-25. В локальном режиме номер вычисляет модель; в production его обязан атомарно назначать сервер.

### Удаление и восстановление

У каждой карточки слайда есть отдельная кнопка корзины (она не вложена в кнопку открытия задачи). Также «Удалить задачу» доступно в общей форме задачи, если она открыта из редактора презентации.

`onDeleteIssue(issue)` → `Workspace.deleteTarget` фиксирует ID/версию → `DeleteIssueDialog` объясняет, что задача исчезнет из проекта и всех презентаций → после подтверждения `data.execute("issue.archive", id, {}, version)`.

Это soft delete через `archivedAt`, без изменения schemaVersion. Модель оставляет запись и комментарии, увеличивает version/revision, пишет event/receipt. Активные доски, личный список, поиск, прогресс проектов и все слайды исключают такую задачу. Если задача изменилась после открытия подтверждения, оно требует пересмотра; ошибка записи не закрывает окно как успешное удаление. Номер удалённой задачи не выдаётся новой.

«Удалённые (N)» внизу слайда открывает `DeletedIssuesDialog` со всеми удалёнными задачами именно его проекта — фильтры статуса и исполнителя не применяются. Восстановление отправляет `issue.restore` с текущей версией. Сохраняются ID, номер, статус, срок, исполнитель и комментарии. После восстановления задача видна на слайде только при соответствии его фильтрам. Архивный проект не допускает восстановление.

Удаление/восстановление работают и во время показа. Слой модального окна расположен выше показа/формы задачи; Escape отменяет подтверждение, не закрывая презентацию. Состояние хранится в общем snapshot, поэтому раздел «Удалённые» сохраняется после перезагрузки. Физического удаления из БД в этой функции нет.

## 8. Отбор задач и автоматический масштаб

`ticketLayout(issues, slide)`:

1. Исключает архивные задачи и задачи другого projectId.
2. Применяет выбранные статусы и необязательный assigneeId.
3. Формирует колонки в порядке backlog → planned → progress → review → done.
4. В каждой колонке сортирует по приоритету high/medium/low, затем дедлайну (без даты — в конце), затем строковому identifier.
5. Вычисляет плотность по самой длинной колонке, не по общему числу задач.

| Максимум задач в колонке | Режим |
| --- | --- |
| 0–4 | comfortable: обычные карточки |
| 5–7 | compact: меньше высота/шрифт, часть полей скрыта |
| 8–12 | dense: плотные строки, детали доступны при открытии |
| >12 | dense + страницы задач, максимум 12 строк в колонке на страницу |

Формулы текущей реализации: `pageSize = min(max(1, rows), 12)`, `pageCount = max(1, ceil(rows / 12))`; высота карточки ограничивается 100 px и оставшимся пространством из 440 px с промежутками 6 px.

У всех колонок общий номер страницы. Например, 25 задач в одной колонке дают три страницы; короткая соседняя колонка может быть пустой на поздних страницах. Общее количество и счётчики колонок относятся ко всей выборке. Страница сбрасывается при смене слайда, проекта или фильтров.

Сам шаблон имеет размер 1280×720. `ResizeObserver` измеряет ширину контейнера, `SlideCanvas` применяет `transform: scale(width / 1280)`. Для текста отдельно вычисляется уменьшение по высоте блока. Это не свободный canvas-редактор и не бесконечное уменьшение всех тикетов: после 12 строк включается пагинация.

Недоступный/архивный проект показывает заглушку; другой проект вместо него не подставляется.

## 9. Markdown и режим показа

Локальный `Markdown`-компонент поддерживает абзацы, строки заголовков `#`–`###`, маркированные строки `-`/`*`, `**жирный**` и встроенный код в обратных кавычках. Это ограниченный синтаксис: таблицы, изображения, ссылки как кликабельные элементы, вложенные списки и блоки кода не реализованы. Заголовки разных уровней отображаются одним стилем.

Рендерер создаёт React-элементы, не использует `dangerouslySetInnerHTML`, не исполняет HTML/MDX/JavaScript. Конфигурация задач не извлекается из Markdown при обычном редактировании.

Режим показа — overlay внутри приложения, не браузерный Fullscreen API. Он использует тот же `SlideCanvas`, поэтому задачи интерактивны и здесь. Стрелки переключают слайды, Escape закрывает показ; события ввода в формах не должны перелистывать слайды. Страницы задач переключаются отдельными кнопками внутри слайда.

Заметки открываются по кнопке на том же экране. Отдельного окна докладчика нет: при демонстрации всего экрана открытые заметки видны аудитории.

## 10. Хранение, миграция и ошибки

`useWorkspace()` выбирает репозиторий по `VITE_DATA_MODE` и является общим владельцем подтверждённого snapshot. Одновременно отправляется одна команда; старый ответ загрузки не заменяет snapshot с большей revision.

### Локальный режим — работает сейчас

- `club-os-workspace-v2` в localStorage: сущности, события, receipt IDs и revision одним JSON-значением.
- `club-os-deck-draft:<presentationId>` в sessionStorage: несохранённый deck и baseVersion.
- Репозиторий использует Web Locks, если доступны, и проверяет последнюю revision перед записью.
- Storage events обновляют другие вкладки. Без Web Locks локальная защита не равна серверной транзакции.
- `applyCommand()` проверяет модель/expectedVersion, увеличивает версии, добавляет событие и receipt. Успех не публикуется, если запись в localStorage не удалась.
- Повтор локальной команды определяется только по command ID; canonical request hash и полноценная серверная авторизация здесь не реализованы.

При отсутствии v2 читаются старые ключи projects/issues/presentations и legacy slides. `normalizeSlide()` умеет извлечь project из старой строки `<TicketBoard ...>`, после чего хранит обычные поля. Этот парсер оставлен только для миграции. Старые ключи не удаляются; повреждённый JSON не заменяется seed-данными. Когда сохранённых данных вообще нет, используются seeds из `components.jsx`.

Legacy ID сохраняются. Старые даты без года нормализуются в 2026 год — их нужно проверить перед production-импортом.

LocalStorage привязан к origin: другой порт, localhost вместо 127.0.0.1 или другой браузер — другое хранилище. Очистка данных браузера удалит записи. SessionStorage не является долгосрочным бэкапом и может исчезнуть при закрытии вкладки.

### Экспорт и восстановление

«Скачать презентацию JSON» экспортирует только объект деки и её слайды, без задач проектов. Отдельного импорта такого файла в UI пока нет.

Настройки экспортируют полный workspace snapshot. Локальное восстановление проверяет его, резервирует предыдущее состояние и увеличивает revision/версии существующих сущностей, чтобы черновики других вкладок стали устаревшими. Это восстановление пространства целиком, не merge. Импорт в API-режиме не реализован.

События — журнал действий, не полная история версий презентации: `changes` не содержит полных массивов slides/comments. Undo/redo и восстановление произвольной прошлой версии по журналу не реализованы.

## 11. Точка подключения backend

`createHttpRepository()` уже реализует:

```text
load()            → GET  /api/v1/workspace
execute(command)  → POST /api/v1/commands
успешный ответ    → { snapshot: WorkspaceSnapshot }
```

Запрос команды содержит `id`, `type`, `entityId`, `data`, `actorId` и expectedVersion для изменения существующей записи. Заголовок `Idempotency-Key` равен command.id. Используются credentials include и timeout 15 секунд.

В API-режиме команда до отправки записывается в sessionStorage. Сетевая ошибка, 5xx или некорректный ответ сохраняют её для явного повтора с тем же ID. Другая запись блокируется до разрешения неопределённого результата. Полноценной offline-очереди нет; API не подменяется локальными демоданными.

Обновление API происходит каждые 15 секунд в видимой вкладке и при возвращении фокуса. Это polling, не WebSocket/SSE. Собственные изменения видны сразу после подтверждённого ответа.

Cloudflare Worker, D1 deployment, авторизация, permissions и Telegram-бот ещё не написаны в этом проекте. Reference SQL — материал для реализации, не применённая миграция удалённой базы. Worker должен самостоятельно проверять права, версии, ID, время и атомарно фиксировать запись/event/receipt/outbox; не доверять client actorId.

Полные DTO, ошибки, транзакционные требования, миграция и Telegram-outbox описаны в [backend-contract.md](backend-contract.md), таблицы — в [cloudflare-schema.sql](cloudflare-schema.sql).

## 13. Что учитывать следующему разработчику

- Не добавлять отдельное хранение задач для презентаций. Все мутации идут через общий `data.execute()`.
- Не заменять dirty deck свежим snapshot без сравнения версий; при обновлении задачи не сохранять всю презентацию.
- При изменении slide schema обновлять `makeSlide`, `normalizeSlide`, `validateSnapshot`, renderer, контракт API, SQL и тесты совместно.
- При изменении раскладки править `ticketLayout` вместе с CSS и проверять 0, 1, 12, 13 и 120+ задач, разные колонки и фильтры.
- Архивный дек блокирует редактирование своей структуры. Живые задачи в его слайдах сейчас всё ещё можно редактировать — архив деки не является запретом записи в проект.
- Deep links `?issue=<id>` и `?presentation=<id>` обрабатываются при начальной загрузке. Полного URL-router, синхронизации истории навигации и публичного sharing-flow нет.
- Клиентские проверки — UX, не security boundary. Auth, разграничение доступа, надёжные транзакции, бэкапы БД и уведомления остаются серверной работой.
- PPTX/PDF export, свободное размещение объектов, мультимедиа, drag-and-drop порядка слайдов, undo/redo и исторические snapshots встреч не реализованы. Перестановка слайдов сейчас выполняется кнопками вверх/вниз.

Продуктовый контекст: [production.md](../production.md). Этот документ описывает именно устройство реализованного модуля презентаций.
